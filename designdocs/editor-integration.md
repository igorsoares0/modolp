# Editor integration — what the landing needs from `app.getmodo.pro`

> Written from the landing repo (`modolp`), August 2026.
>
> **What this is:** the interface between the two repos, specified from the side
> that consumes it. The landing is the only acquisition surface Modo has; the
> editor's job in SEO terms is to (a) stop competing with it and (b) not drop the
> visitors it sends.
>
> **What this is not:** an implementation plan. Whoever picks this up has the
> editor's source and this document's author did not — every "how" below is a
> suggestion, every "what" is a requirement. If the editor already does one of
> these, say so and strike it.

---

## Why any of this

`getmodo.pro` is where content ranks. `app.getmodo.pro` is a gated editor that
should never rank for anything. Google treats subdomains as partially separate
properties, so any content or authority that accumulates on the app side is
authority the landing does not get.

That gives the editor exactly two jobs here:

1. **Stay out of the index**, so it never competes with the landing for brand
   terms and never splits authority.
2. **Honour the intent** of visitors the landing sends — they arrive from a
   search, cold, with a specific canvas in mind.

Item 3 below is different in kind: it is the editor *supplying* the landing with
the assets that unlock the largest content family we have.

---

## 1. Indexing hygiene

**Effort:** ~30 minutes. **Do this first** — it is the cheapest item here and the
only one that is currently losing something.

### The finding

As of **2026-08-09**, `https://app.getmodo.pro/robots.txt` returns **404**. No
robots.txt means crawlers assume everything is allowed. `/signup` responds
publicly with the title `Create account — Modo`.

Caveat, stated plainly: this was checked with a fetch tool that converts pages to
markdown, so it may not surface `<head>` meta tags. **The missing robots.txt is
confirmed; a missing `noindex` is suspected, not proven.** Check the raw HTML
before assuming there is a problem.

### What's needed

**A robots.txt that disallows everything.** The whole subdomain, not selected
paths — there is no page on the editor that benefits from ranking:

```
User-agent: *
Disallow: /
```

The editor is on Next.js 16 too, so `app/robots.ts` works the same way it does in
this repo (see `app/robots.ts` here for the inverse).

**`noindex` on any publicly reachable route**, belt-and-braces, since robots.txt
governs crawling rather than indexing and a URL linked from elsewhere can still
surface. In App Router that is:

```ts
export const metadata: Metadata = {
  robots: { index: false, follow: false },
};
```

The routes that matter are the ones reachable without a session — at minimum
`/signup` and `/login`, plus any password-reset or email-verification landing.

### Why it matters

`/signup` on the editor competes with the landing for brand queries
("modo design", "modo editor") and loses on conversion: a cold visitor from
search meets an account form instead of an explanation of the product. The
landing is the page built to answer that query.

## 2. The `?format=` contract

**Effort:** small, but it crosses the auth flow. **This is the item that decides
whether the SEO work converts.**

### What the landing already emits

Live now, on all three pages under `/sizes/*`. Generated by
`signupUrlForFormat()` in `app/lib/site.ts`:

| Landing page | CTA links to |
| --- | --- |
| `/sizes/instagram-post` | `https://app.getmodo.pro/signup?format=instagram-post` |
| `/sizes/instagram-story` | `https://app.getmodo.pro/signup?format=instagram-story` |
| `/sizes/pinterest-pin` | `https://app.getmodo.pro/signup?format=pinterest-pin` |

The slugs are the canonical identifiers, defined in
`app/lib/content/formats.ts`. They map to canvases as:

| Slug | Canvas |
| --- | --- |
| `instagram-post` | 1080 × 1080 |
| `instagram-story` | 1080 × 1920 |
| `pinterest-pin` | 1000 × 1500 |

If the editor already has its own identifiers for these canvases and they differ,
**tell the landing and we will change ours** — one of the two sides has to give,
and the landing is the cheaper side to change.

### The requirement

Read `format` on arrival, and **carry it through signup and email verification**,
so that the first screen after verification is that canvas — not a dashboard.

The middle part is the whole point and the part that is easy to miss. The flow is:

```
/signup?format=instagram-story
  → account created
  → "check your email"
  → click the link in the email          ← the param must survive this hop
  → verified
  → editor opens on a 1080 × 1920 canvas
```

The email-link hop is where intent normally dies, because the link is generated
server-side and typically points at a fixed destination. Whatever mechanism is
used — pending-intent row against the user, signed state in the verification
token, a cookie set before signup — it has to outlive a round trip through the
user's inbox, possibly in a different browser.

### Current behaviour and blast radius

The param is ignored today, so the link degrades to a normal signup. Nothing is
broken. But every visitor who clicks *"Open a 1080 × 1920 canvas"* lands on an
empty dashboard — the highest-intent traffic the landing produces, dropped at the
last step. Traffic is near zero right now, which is exactly why this is worth
doing before it isn't.

### Later, same mechanism

Once intent survives the auth flow, `?prompt=` becomes possible: a landing page
could send `?format=instagram-story&prompt=launch%20post%20for%20a%20matcha%20caf%C3%A9`
straight into a generation. Not needed now — but if the intent-preservation
mechanism is built generically rather than as a single `format` field, it costs
nothing to leave the door open.

## 3. Template preview manifest

**Effort:** the real work here. **Payoff:** unblocks the largest content family
available to us.

### Why this is the high-leverage item

Everything the landing can write without the editor tops out at roughly 15 pages.
The template gallery is 45+ pages that grows every time a template is added. This
is how Canva ranks for essentially everything — their template pages *are* the
SEO machine.

The landing cannot build any of it today, because it has neither the template
data nor a renderer. The `editor-mock.tsx` in this repo is a hand-drawn replica,
not real data.

**A template page without a real preview image is thin content**, and publishing
45 of them would do more harm than publishing none. So this is strictly blocking.

### What the landing needs

Two artifacts, published to a stable public location (R2 is already in the stack):

**1. A manifest JSON**, one entry per template:

```jsonc
{
  "generatedAt": "2026-08-09T12:00:00Z",
  "templates": [
    {
      "slug": "matcha-cafe-launch",        // stable, URL-safe, never reused
      "name": "Matcha Café Launch",
      "category": "Food",                   // one of the 45
      "format": "instagram-post",           // same vocabulary as §2
      "isPro": false,
      "palette": ["#1b1a18", "#eceae5"],    // dominant colours, for the page
      "fonts": ["Instrument Sans"],
      "preview": {
        "width": 1080,
        "height": 1080,
        "sizes": {
          "thumb": "https://.../matcha-cafe-launch-400.webp",
          "full":  "https://.../matcha-cafe-launch-1080.webp"
        }
      }
    }
  ]
}
```

**2. The preview images themselves**, at the URLs the manifest points to.

### Requirements on that data

- **Slugs must be stable and never reused.** They become URLs
  (`/templates/matcha-cafe-launch`). A slug that changes is a dead page; a slug
  that gets reused for a different template is worse. If a template is retired,
  the slug retires with it.
- **Two image sizes minimum** — a grid thumbnail (~400px) and a detail view
  (full canvas width). WebP preferred, with the real aspect ratio preserved.
- **Categories from a fixed vocabulary.** Free-text categories generate garbage
  URLs. The 45 categories should be an enum on the editor side.
- **Regenerated on template change**, not by hand. If adding a template does not
  automatically produce its preview, the manifest goes stale and the pages start
  lying.
- **Publicly readable without auth**, since the landing fetches it at build time
  and browsers fetch the images.

### How the landing will consume it

Build-time fetch, then static prerender — same as `/sizes` and `/vs`. That means:

- **The manifest URL must be stable**, since it goes in the landing's build.
- **A failed fetch must not break the build.** The landing will need to fall back
  to the last known-good manifest or skip the family entirely; that is the
  landing's problem to solve, but it is worth knowing that a flaky endpoint
  degrades to "no template pages", not "broken deploy".
- **A rebuild is required to pick up new templates.** Fine at this cadence. If it
  stops being fine, the landing switches that family to ISR.

### Suggested shape, not a requirement

A script in the editor repo that renders each template headless, writes both
image sizes and the manifest, uploads to R2, and runs in CI on template change.
The editor already has Konva and an R2 client; whether headless rendering reuses
the canvas renderer or goes through a browser is a call for whoever has the code.

## 4. Domain rules

- **No marketing or editorial content on `app.getmodo.pro`.** Blog posts, guides,
  template galleries, comparison pages — all of it belongs on the root domain.
  Content on the subdomain is authority the landing does not get.
- **If anything public ever does appear on the app subdomain**, it needs a
  canonical pointing at the root-domain equivalent.
- **The subdomain-vs-path decision stays open.** Moving `app.getmodo.pro` to
  `getmodo.pro/app` would consolidate authority completely. It is cheap now
  (no accumulated authority to lose) and expensive later (session cookies, auth
  domain, redirect chains). Current recommendation is **stay on the subdomain** —
  the gain is marginal, the auth cost is not — but it should be a decision that
  was made, not one that was defaulted into. Revisit before the template gallery
  ships, because that is when authority starts accumulating for real.

## Sequence

| # | Item | Effort | Blocking what |
| --- | --- | --- | --- |
| 1 | robots.txt + `noindex` | ~30 min | Nothing, but losing brand terms now |
| 2 | `?format=` through auth | Small, crosses auth flow | Conversion of all `/sizes` traffic |
| 3 | Preview manifest | The real work | ~45 pages of `/templates/*` |
| 4 | Domain rules | Ongoing discipline | — |

Items 1 and 2 are worth doing this month. Item 3 is worth starting when there is
a real block of time; it is the only one that changes the ceiling.

## Open questions

Things this document guesses at, and whoever implements it can settle:

- Does the editor already have canvas identifiers? If so, do they match the three
  slugs in §2, and which side changes?
- Is there an existing signup-intent mechanism (a `redirect` or `next` param)
  that `format` can ride on instead of a new one?
- Does the verification email link already carry state, or is it a bare token?
  That determines how hard §2 actually is.
- Are template slugs already stable and unique, or are templates currently
  identified by array index / display name?
- Is there an existing headless render path (export uses one server-side?), or
  would previews be the first?
